# Chapter 17 — Normative Language

> **Normative language establishes the level of obligation associated with every requirement defined in Simplicion Academy Foundation Standards. It ensures that all standards are interpreted consistently across educational, technical, operational, and governance contexts.**

---

# 17.1 Purpose

This chapter defines the official normative language used throughout Simplicion Academy Foundation Standards (SAFS).

Normative language communicates whether a statement is:

- Mandatory
- Recommended
- Optional
- Prohibited
- Informational

Every SAFS and SACOS document MUST interpret these terms exactly as defined in this chapter.

---

# 17.2 Scope

This chapter applies to:

- Foundation Standards
- Content Standards
- Platform Standards
- Governance Documents
- Policies
- Procedures
- Technical Documentation
- Educational Documentation

No alternative interpretation of normative terminology is permitted.

---

# 17.3 Normative Keywords

The following keywords have official meanings.

| Keyword | Meaning |
|----------|---------|
| MUST | Absolute requirement |
| MUST NOT | Absolute prohibition |
| REQUIRED | Mandatory requirement |
| SHALL | Mandatory obligation |
| SHALL NOT | Mandatory prohibition |
| SHOULD | Strong recommendation |
| SHOULD NOT | Strong recommendation against |
| RECOMMENDED | Preferred approach |
| MAY | Optional implementation |
| OPTIONAL | Entirely discretionary |

---

# 17.4 MUST

## Definition

**MUST** indicates an absolute requirement.

Failure to comply constitutes non-conformance with the applicable standard.

### Example

- Every Learning Unit **MUST** have a unique identifier.
- Every published document **MUST** include metadata.

---

# 17.5 MUST NOT

## Definition

**MUST NOT** indicates an absolute prohibition.

Actions described using this keyword are never permitted.

### Example

- Deprecated terminology **MUST NOT** be used in new documentation.
- Object identifiers **MUST NOT** be modified after publication.

---

# 17.6 REQUIRED

## Definition

**REQUIRED** identifies an element that is mandatory for compliance.

It carries the same level of obligation as **MUST**.

### Example

- Version information is **REQUIRED**.
- Owner metadata is **REQUIRED**.

---

# 17.7 SHALL

## Definition

**SHALL** expresses a mandatory obligation, typically used in governance, policy, and procedural statements.

### Example

- Every standard **SHALL** undergo periodic review.
- Every published document **SHALL** be version controlled.

---

# 17.8 SHALL NOT

## Definition

**SHALL NOT** expresses a mandatory prohibition.

### Example

- Archived standards **SHALL NOT** receive content updates.
- Duplicate object identifiers **SHALL NOT** exist.

---

# 17.9 SHOULD

## Definition

**SHOULD** indicates a strong recommendation.

Alternative approaches may be acceptable when supported by valid justification.

### Example

- Learning Units **SHOULD** include practical examples.
- Assets **SHOULD** be reusable across multiple Modules.

---

# 17.10 SHOULD NOT

## Definition

**SHOULD NOT** indicates that an action is generally discouraged.

Exceptions may exist but require documented justification.

### Example

- Documents **SHOULD NOT** contain duplicate definitions.
- Assets **SHOULD NOT** duplicate existing resources.

---

# 17.11 RECOMMENDED

## Definition

**RECOMMENDED** identifies the preferred approach without making it mandatory.

Organizations may adopt alternative methods when appropriate.

### Example

- Mermaid diagrams are **RECOMMENDED** for process visualization.
- Markdown is the **RECOMMENDED** source format.

---

# 17.12 MAY

## Definition

**MAY** indicates an optional capability or implementation.

Choosing not to implement an optional feature does not affect compliance.

### Example

- Learning Units **MAY** include downloadable templates.
- Assessments **MAY** include peer review activities.

---

# 17.13 OPTIONAL

## Definition

**OPTIONAL** indicates complete implementation flexibility.

Its inclusion is left entirely to the discretion of the document owner.

### Example

- Glossaries are **OPTIONAL** for small reference documents.
- Supplemental reading lists are **OPTIONAL**.

---

# 17.14 Informative Statements

Statements that do not contain normative keywords are considered informative.

Informative statements:

- Explain concepts.
- Provide context.
- Offer examples.
- Improve understanding.

They do not establish compliance requirements.

---

# 17.15 Compliance Interpretation

Compliance shall be evaluated according to the normative keyword used.

| Keyword | Compliance Required |
|----------|--------------------|
| MUST | Yes |
| MUST NOT | Yes |
| REQUIRED | Yes |
| SHALL | Yes |
| SHALL NOT | Yes |
| SHOULD | Normally |
| SHOULD NOT | Normally |
| RECOMMENDED | Preferred |
| MAY | Optional |
| OPTIONAL | Optional |

---

# 17.16 Writing Guidelines

Authors of Foundation Standards should:

- Use **MUST** only for mandatory requirements.
- Use **SHOULD** for recommendations.
- Use **MAY** only for optional features.
- Avoid mixing multiple normative keywords within a single requirement.
- Write requirements clearly and unambiguously.

Normative statements should express one requirement at a time.

---

# 17.17 Interpretation Rules

When interpreting Foundation Standards:

- Every normative keyword shall retain its official meaning.
- Context shall not weaken mandatory requirements.
- Informative examples shall not override normative requirements.
- In case of conflict, the stricter normative requirement takes precedence.

---

# 17.18 Common Mistakes

Avoid:

- Using **MUST** for personal preferences.
- Using **SHOULD** when a requirement is mandatory.
- Using **MAY** for required behavior.
- Mixing mandatory and optional language within the same sentence.
- Using undefined obligation terms such as "needs to" or "is expected to" in normative requirements.

# Summary

Normative language defines how every requirement within Simplicion Academy Foundation Standards is interpreted and enforced.

By standardizing the meaning of obligation keywords, the Academy ensures that all educational, technical, operational, and governance documents communicate requirements consistently, eliminating ambiguity and supporting reliable implementation across the entire ecosystem.
